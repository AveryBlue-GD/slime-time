# Claude Pixel Game Test — "Slime Maze"

2D pixel-art game in **Godot 4.7** (GDScript). A slime glides through a pitch-black maze; its goo trail reveals the map, moving drains the slime meter, and a golden chalice is the exit. Full design and build phases: [docs/game-design.md](docs/game-design.md). **Phases 1-4 are done**; next is Phase 5 (skins, palette-swap shader, unlocks, post-game color wheel + glow).

## Pixel-art rules (keep these consistent)
- Base resolution **320x180**, window 1280x720, stretch mode `viewport` + `integer` scaling.
- **16x16 tiles**, characters roughly 16x16. Nearest-neighbor filtering is the project default; never enable texture filtering.
- `snap_2d_transforms_to_pixel` is on; avoid sub-pixel scaling or rotation of sprites.
- Colors come from the palette in `tools/make_placeholder_art.py` (`PAL`). New art should reuse it.

## Layout
- `scenes/main.tscn` — a level (script `scripts/game.gd`): Floor/Walls TileMapLayers, Trail + Fog image overlays, Chalice, Slime, HUD
- `scripts/game.gd` — level setup (maze + tile variant choice), fog/trail reveal on a 2 px grid with stepped fade-back (`FADE_AFTER`/`FADE_ALPHA`, drawn by `assets/shaders/fog.gdshader`), slime cost, win/lose, next level
- `scripts/maze_generator.gd` — `MazeGenerator`: seeded growing-tree maze (1-tile corridors and walls), shortest path, dead-end count
- `scripts/levels.gd` — `Levels`: the 10 level configs (size, seed, branching, slime target) and tile weights. **Tune difficulty here.**
- `scripts/progress.gd` — autoload `Progress`: levels cleared/unlocked, current level, saved to `user://save.cfg`
- `scripts/slime.gd` — `Slime` (radius 7, snug in 16 px corridors; single-axis input centers it in its lane): gliding + charge jump state machine (GLIDE/CHARGING/AIRBORNE/STUNNED); `scripts/jump_guide.gd` — charge meter + landing dots
- `scripts/hud.gd` — slime meter + messages; `scripts/chalice.gd` — chalice sparkle
- `assets/sprites/` — PNGs generated by `python tools/make_placeholder_art.py`: `slime_sheet.png` + `slime_sheet.json` (48 animations in 20x20 frames, built into SpriteFrames by `Slime.load_sprite_frames()`; frames for charge/air/splat are picked by game state), `chalice_sheet.png`, `shadow.png`, `walls.png` (16 neighbor masks x 4 damage x 3 styles), `floors.png` (8 types x 4 variants)
- `tests/` — `test_phase1-4.gd` (headless checks; phase 3 plays all 10 levels with the autopilot; phase 4 covers animations and fading), `autopilot.gd` (drives the slime along the shortest path), `demo.tscn` (game + autopilot) and `demo_jump.tscn` (splat + charging) for screenshots

## Commands (PowerShell, from project root)
Godot isn't on PATH; `tools/godot.ps1` finds the winget-installed console binary.
- Re-import assets after adding/changing files: `.\tools\godot.ps1 --path . --headless --import`
- Smoke-run for errors: `.\tools\godot.ps1 --path . --headless --quit-after 10`
- Tests (run each): `.\tools\godot.ps1 --path . --headless --fixed-fps 60 --quit-after 5000 -s res://tests/test_phase2.gd` (prints `RESULT: PASS`; `--quit-after` stops a test that errors out instead of hanging)
- Screenshot: `.\tools\screenshot.ps1 [-Frames 30] [-Scene res://tests/demo.tscn]` → `.screens/latest.png` (view it with Read). Use the demo scene with ~700 frames to see a mid-run state; add `-Level N` for a specific level.
- Inspect a screenshot up close: `python tools/upscale_png.py .screens/latest.png .screens/zoom.png 4 [x y w h]`

## Workflow
- After gameplay or visual changes: run the tests and take a screenshot to confirm before reporting done.
- Input actions in `project.godot` `[input]`: `move_left/right/up/down` (WASD + arrows), `jump` (Space), `restart` (R).
- The Godot editor may be open and rewrites `project.godot` in its own format; keep edits compatible.
- Write files as UTF-8 without BOM (PowerShell's `Set-Content -Encoding utf8` adds one).
- Commit working states with git so changes can be rolled back.
